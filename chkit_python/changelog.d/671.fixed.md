Async `migrate --apply` no longer journals a step as failed when the submit request fails
with a transport error (e.g. a gateway 524) before any poll saw the query running (#671): the
server may be running the query unobserved, so the step now polls through the same bounded
grace, and stays `started` for a re-run to attach to if no trace appears. A server rejection
still fails at once: it carries ClickHouse's exception code, relayed by the direct client in
its error message (a gateway non-2xx without one does not count) and kept from the server's
error text by the ObsessionDB console executor. Relayed network codes (209, 210) and code 216
(a query with the same id still running) are not rejections.
Rejections are also recognized with clickhouse-connect 0.8.x, including its header-only and newline-prefixed server-body messages.

# Stable registry syncs

Apply this contract when authoring or improving registry providers. Select mechanisms from official provider documentation and observed response shapes; do not invent change filters or durable cursors. Preserve explicit user constraints. A provider limitation calls for safe replay and an honest coverage statement.

## Establish the source contract

For each resource, record the account/query scope, stable record identity, bootstrap coverage, filter timestamp meaning, ordering, boundary inclusivity, pagination guarantees, cursor lifetime, and retention. Check whether edits, deletions, and child-only changes update the selected timestamp. Determine whether pages are snapshots, live mutable lists, or a change feed. Verify filter/token incompatibilities and provider caps on child collections.

Choose the strongest appropriate mechanism, independently for each resource:

| Provider contract | Selection and durable progress |
| --- | --- |
| Change feed or sync token | Bootstrap completely, retain the input token throughout pagination, and promote a terminal replacement token only after all corresponding writes |
| Reliable modification filter | Fixed upper cutoff and overlapping lower bound; checkpoint a fully consumed window or independently complete bounded interval |
| Creation-time filter | Use for proven immutable events or parent discovery; distinguish discovery progress from freshness, and retain delayed-child work/reconcile later edits separately |
| Full mutable listing | Use `fullSync()` with ordinary pagination and journaled execution completion; replay an interrupted stream from the beginning when offsets are mutable. Add finer progress only when the collection's cost and provider contract justify it |

A full read is appropriate when the API lacks a reliable change mechanism and its complete cost is acceptable. For a registry resource, explain that choice. The executor records successful work, including empty `fullSync()` executions; do not add cycle counters or state-only markers merely to duplicate that completion. A creation timestamp is not a modification cursor; a pagination cursor is not automatically a change token. Runtime `cursorState()` can implement a full scan, so the helper alone does not determine the manifest's strategy label.

Choose meaningful stream boundaries before designing custom recovery. Use one pipeline per account or installation, with one independently selectable stream per resource type or configured collection. Attio demonstrates independent People/Companies readers sharing a raw records table and using ordinary full-sync pagination. Individual entities stay inside their resource stream; do not make a stream per person, meeting, message, or task. GitHub separates issues, PRs, comments, reviews, commits, and stargazers for each repository, while Slack channels are traversal scope inside its messages stream. Pipelines share execution defaults, not durable progress or discovery order. Each resource resolves its own configured parents, so a failure or selection in another resource cannot block discovery or parent publication.

Prefer existing pagination and checkpoint primitives. Separate editable configuration, authenticated requests, pipeline composition, and meaningful resource readers when those responsibilities warrant modules; avoid empty proxy files. Pipeline factories must bind the supplied account/filter configuration to readers and strategies consistently. Exported raw tables are setup-time schema definitions: document that changing runtime reader settings does not redefine storage. Extract genuinely repeated mechanics into the library rather than copying a generic state machine into each provider. Native sync tokens, fixed-window frontiers, delayed-child queues, and acknowledged parent traversal can still require provider-owned state; removing generic boilerplate must preserve those invariants.

Use `paginate<TItem, TCursor, TMetadata>` for page transport: its result retains `items`, `next`, and optional metadata, including empty pages. The reader maps `page.items` to rows and safe metadata to a chunk's `state`; `cursorState` and the executor already own persistence after acknowledgement. A sync-token adapter retains the input sync token alongside nonterminal page progress, then supplies a terminal replacement token with no next-page continuation. Yield that terminal checkpoint even when its items are empty. Repeated continuations are rejected before their page is exposed. Do not create singleton-item wrappers or manual loops merely to preserve page metadata; protocol resets and parent discovery can still need provider logic.

Calendar represents a validated token reset as an empty page with a fresh compound continuation and checkpointed recovery debt, keeping it inside one paginator. Slack uses `next` only to cross empty or parent-only message pages, while native `has_more` metadata guides the reader's next durable timestamp interval. Keep generic continuation checks in `paginate`; retain provider-specific validation and state needed for recovery or unfinished child work.

In a chkit checkout, inspect relevant `registry/<provider>/` implementations and tests. Calendar demonstrates terminal sync-token promotion; Slack fixed timestamp frontiers and retained threads; Meet late artifacts and nested participant/session cursors; Circleback independent full reads and complete meeting-transcript snapshots; GitHub independent raw parent/child resources with child-owned windows; Linear independent resource windows and full-history discovery; Lemlist completed activity intervals alongside complete full reads. Apply their recovery invariants to the normalized raw resource model, with dates, budgets, and account scope chosen for the new provider. Consult Brain's provider implementations when available while keeping its application projections out of raw registry schemas.

## Keep progress recoverable

- Bind stream IDs and saved state to stable non-secret source, account, and query identities. Check authenticated identity when the provider exposes it; otherwise require new stream/destination identities when switching accounts. Credentials themselves must not become checkpoint scope. Validate saved types, bounds, parent positions, and scope before reuse. Version custom strategies and document migrations.
- Separate completed coverage from unfinished work. Persist fixed window bounds and enough scoped page/parent/child position to resume them; recomputing a cutoff must not move an unfinished selection. Preserve exact provider timestamp precision and handle equal timestamps without skipping records.
- When custom progress is necessary, yield fresh, complete candidate state. The executor owns its durable commit after destination evidence. Never advance a watermark past rows or required work that is neither loaded nor durably retained. Empty terminal pages must also commit required token/watermark progress; use state-only markers or batching that flushes those safe boundaries. Ordinary empty full-sync success needs no custom marker.
- Persist offsets or opaque page tokens only under a documented resumption contract. Expiring page tokens can be saved while valid if state also retains the original input and a safe recovery path. For mutable offset lists, restart the interrupted stream's collection at zero. If justified custom state tracks multiple work units within a stream, skip acknowledged units only within the saved selection and restart its unfinished mutable unit. Frozen selection means unchanged predicates and retained discovered parent IDs, not a frozen source dataset. Coverage still depends on provider ordering, snapshots, or eventual stability plus reconciliation. A completed cycle resets any such progress and selects current work again.
- On an expired token, replay the same scoped collection from its committed input or rebuild a baseline as the provider requires. Bound protocol resets across the unfinished selection, not just one process: retain reset debt or detect repeated recovery without useful durable progress. Repeated rejection/stalled recovery fails visibly. Keep existing raw observations during baseline recovery. Absence from a rebuilt baseline is not automatically deletion.
- Treat explicit backfills as separate checkpoint namespaces. Honor both bounds for historical selection. Reject unsupported bounds when the reader can enforce that contract, or document that a simple full-sync reader ignores bounds and provides no date-range backfill. Retain the original unfinished bounds for supported backfills, reject incompatible reuse of a backfill ID, and prevent interval watermarks from regressing. A bundled helper ignoring `range` does not establish historical-range coverage.

## Preserve raw data and delayed children

Recommend normalized raw sync by default: one raw stream and destination per meaningful resource type, synced as directly as possible from the provider. Preserve complete provider objects, including sparse cancellation payloads, with stable source/parent/provider keys. Normalization separates resource collections; it does not require flattening or renaming the provider's fields. Readers handle retrieval and recovery with minimal identity/envelope mapping. Perform field transformations, business mappings, enrichment, joins, and denormalization afterward in ClickHouse SQL views, materialized views, or derived tables; use an ingestion projection only when explicitly requested.

Each child reader resolves parents from configured identity or its own discovery, then pages raw child rows. Stream order is not a dependency contract and child completion does not gate raw parent publication.

Validate complete resource coverage rather than accepting endpoint defaults. A capped list with no continuation may require the provider's complete export endpoint; a default incomplete-only or current-user filter requires verified status/ownership partitions. Retrieve complete same-resource detail when a list deliberately omits fields, without assembling unrelated resource records. Reads must remain read-only: explicitly disable retrieval side effects such as an inbox endpoint's default mark-as-read behavior. Preserve native nested fields and links; binary downloads and extra metadata resources require their own scope decision.

Use a child's reliable update filter for its own incremental window; do not restrict parent discovery by a parent watermark unless the provider guarantees that all child changes advance it. Otherwise revisit all eligible parents with ordinary pagination/fullSync, or retain necessary delayed-artifact recovery so late children on old parents remain visible. Choose overlap and reconciliation cadence from provider retention, delay, volume, and freshness requirements.

Embed children only for an explicit document model or an inseparable bounded provider object. In that model, a child failure must not publish an incomplete document as complete: finish required children or retain durable pending work and explicit completion semantics. Retain relevant parents for delayed recordings/transcripts rather than removing recovery merely to simplify the table model.

Bound pending queues and in-memory work; fail visibly rather than silently dropping entries. Pending work that expires before collection is a coverage gap. Distinguish unavailable, forbidden, not-found, and still-processing outcomes using provider evidence. Diagnostics are not a retry queue unless the reader actually executes them.

Mutable row chunks should normally omit explicit chunk IDs so changed observations remain eligible for publication. Stable page numbers, offsets, cursor strings, and interval labels can suppress changed replay content. Explicit data-bearing IDs require immutable, repeatable content; state-only progress markers may use logical boundary IDs. Stable row IDs handle repeated observations, separately from batch deduplication.

Raw destinations retain latest observed records unless a stronger current-state protocol exists. Consume explicit deletion signals when supported. Do not infer deletion from partial, failed, inaccessible, or expired scans. Removing unseen records requires a separately designed completed-generation reconciliation.

When recording retrieval availability, keep its observation separate from successful resource content. A later permission failure or not-found response must not replace previously collected content with null; an actual successful empty response can replace the same resource snapshot. Distinguish operational availability keys from native resource identities in schemas and documentation.

## Bound execution and prove recovery

Use executor request/retry/cancellation authority with finite request timeouts. Validate repeated or malformed continuations and absent required terminal tokens. Classify provider-specific rate limits, permanent permission failures, and recoverable protocol resets correctly. Bound chunk sizes and expensive runs; ensure a run budget can reach a useful checkpoint, or partition the selection rather than perpetually replaying an oversized bootstrap.

Use portable fixtures through `runIngestion` with memory journal/destination adapters. Exercise the applicable contracts:

- Interrupt or exhaust a budget mid-window, page, parent, or child; deserialize saved state in a fresh run and verify complete eventual coverage under the original bounds.
- Accept destination rows, then lose the load acknowledgement or fail journal publication; verify replay without skipped rows or an advanced completed frontier. Reader-only tests cannot prove this ordering.
- Commit empty input and empty terminal progress; continue across empty pages that still have a cursor; reject repeated/malformed pagination and malformed or scope-mismatched saved state.
- Expire provider tokens, retain the correct input token across pages, and promote terminal tokens only after writes. Verify bounded recovery instead of an endless reset.
- Cover timestamp ties, exact precision, inclusive/exclusive bounds, overlapping runs, late children/old edits, parent discovery changes, and explicit backfill isolation where supported.
- Replay mutable observations with changed content and unchanged provider IDs. Test child failure/availability/retention behavior instead of silently truncating a document or queue.
- Bind non-default source/filter/page settings through the pipeline factory and verify requests, row identity, and saved scope agree. Select one resource independently and fail a different resource without losing its acknowledged progress. For modular templates, install at a relocated consumer path and verify credential-free discovery, raw schema generation, typechecking, and portable fixture execution.

Mark distributed fixture files with `role: "test"`, include their dependencies, and keep them free of repository-only imports and live credentials. For new packaging or destination changes, verify installed consumers and real ClickHouse JSON/replay behavior in an authorized isolated target; memory adapters do not establish merge or deduplication-window behavior.

Before delivery, align manifest labels, README, and integration guide with implemented coverage, bootstrap, normal sync, resumption, reconciliation, deletion semantics, account changes, backfill support, and tuning. Document row/state identity changes and report the evidence and remaining API limits.

## Keep one release draft per integration

Treat release artifacts already present in the PR's merged base as immutable history. A new artifact on an unmerged PR branch is a draft, even after it is committed or pushed. Each integration has at most one new version artifact in that PR; update the same draft throughout implementation instead of retaining intermediate versions. Choose a new version relative to the latest merged release, then keep it until the PR merges.

Maintain cumulative `meta.chkit.changelog` entries with semantic `version` and `changes` arrays, newest first. The first entry matches the current template version. Consolidate the final user-visible changes and identity migrations in that one entry, and preserve earlier released notes. Do not describe temporary PR revisions as published releases or require migrations from them.

In the chkit checkout, regenerate the selected draft with `bun run registry:release -- --base origin/main <provider>` and run `bun run check:registry-releases -- --base origin/main`. Use the actual PR base if different. The release command rewrites only current drafts absent from that base; the guard verifies one added artifact per integration, unchanged published history, and source/artifact agreement. After merging, further source or metadata changes belong to a new version and changelog entry in a later PR.

Order migration DDL by object dependencies (#231). `chkit generate` sorted creates by kind and then by name, so a migration that recreated stacked views could fail halfway with `Unknown table expression identifier` after its drops had already run. An object is now created after every object it reads and dropped before them. This covers a view that reads another view, a materialized view, a dictionary (`dictGet`, `dictionary()`), or a Join table (`joinGet`), named by a string or an identifier; a created or dropped table whose column `DEFAULT`, `MATERIALIZED`, `ALIAS`, or `EPHEMERAL` expression calls `dictGet`; a materialized view's `TO` table and `DEPENDS ON` views; and a dictionary's ClickHouse `TABLE`/`QUERY` source. References come from qualified `database.name` names and from unqualified `FROM`/`JOIN` targets and name arguments, which resolve against the object's own database. Objects with no dependency inside the migration keep the kind-then-name order; refreshable materialized views are no longer ordered by `DEPENDS ON` targets outside the migration. `ALTER` statements are not reordered, so adding or changing a column whose expression calls `dictGet` on a dictionary created in the same migration, or dropping a dictionary together with the column expression that calls it, still takes two migrations. Renames (`--rename-table`, `--rename-column`, `--rename-dictionary`, or `renamedFrom`) no longer re-sort the plan by name, which used to undo the `DEPENDS ON` order of refreshable materialized views.

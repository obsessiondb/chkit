`chkit plugin backfill submit --plan-id <id>` re-submits a saved plan whose ObsessionDB job failed or was cancelled (#313). Before, `chkit check` kept failing with `obsessiondb_backfill_job_failed` for such a plan, and the only recovery was deleting the plan file by hand or running it locally.

The chunks of the saved plan that never finished are sent as a new job, and its submission file gets the new job ID, so `chkit check` follows the new job. Chunks an earlier job already wrote are left out: writing one again duplicates its rows whenever the second INSERT differs from the first (a table copied into itself reads the rows it wrote), and the job's task counts miss an INSERT that finished after a cancel, so `submit --plan-id` reads `system.processes` and `system.query_log` on every replica of the service for the plan's chunk queries. `--title` and `--concurrency` apply to the new job; planning flags (`--target`, `--cutover`, `--from`, `--to`, `--max-chunk-bytes`) are rejected next to `--plan-id`. `submit --plan-id` reads the current job's status first and starts no job when it is still active (`backfill_resubmit_job_active`), already completed (`backfill_resubmit_job_completed`) or cannot be read (`backfill_resubmit_job_unverified`), when a chunk query of the plan still runs (`backfill_resubmit_chunks_running`), the query log cannot be read (`backfill_resubmit_chunks_unverified`) or every chunk already finished (`backfill_resubmit_nothing_to_run`), when the plan does not exist (`backfill_resubmit_plan_not_found`) or has no submission file (`backfill_resubmit_not_submitted`), or when the flags are invalid (`backfill_resubmit_invalid_flags`). The `--json` error carries the code under `code`; a success adds `planId`, `replacedJobId` and `skippedChunks`. The `obsessiondb_backfill_job_failed` finding now points to `submit --plan-id`. The backfill SDK exports `readPlanSubmission` and `findExecutedChunks`.
